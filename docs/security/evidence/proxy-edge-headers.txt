Edge response headers and TLS policy — caddy/Caddyfile
======================================================
Captured 2026-09-24 against Caddy v2.11.4 (the version docker-compose.yml
pins) running caddy/Caddyfile unmodified except for the listener ports, which
were moved to 9080/9443 so the probe needs no privileged port. The upstream is
a stub that returns 200 with its own Content-Security-Policy and
X-Content-Type-Options and nothing else, which is what makes case A meaningful:
it shows the edge adding the headers the application did not send while leaving
the one it did send untouched.

Supports ASVS v5.0.0-3.4.1 (HSTS on all responses), 3.4.4 (nosniff on all
responses), 3.4.6 (frame-ancestors on all responses) and 12.1.1 (TLS versions).
The gap these close is recorded in evidence/proxy-restart-502.txt: a 502
generated by Caddy while the application container was being replaced carried
no security headers at all and still identified the server.

Reproduce:
  caddy run --config caddy/Caddyfile --adapter caddyfile
  curl -sk -D - -o /dev/null https://<host>/          # A
  <stop the application container>
  curl -sk -D - -o /dev/null https://<host>/items/    # B
  curl -s  -D - -o /dev/null http://<host>/items/     # C
  curl -sk --tlsv1.1 --tls-max 1.1 https://<host>/    # D, must fail
  curl -sk --tlsv1.3 https://<host>/                  # E, must connect
