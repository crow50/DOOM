Client address handling at the edge — caddy/Caddyfile
=====================================================
Captured 2026-09-24 against Caddy v2.11.4, the version docker-compose.yml
pins. Supports ASVS v5.0.0-4.1.3 (an intermediary's header cannot be
overridden by the end user) and 15.3.4 (the original address reaches the
application correctly and is used for rate limiting).

The Caddyfile forwards `{client_ip}` rather than `{remote_host}`. The claim
that this changes nothing for the default deployment, and is correct for a
deployment behind an operator's own proxy, is what these two probes show.
Both sites answer with both placeholders; the request carries a forged
X-Forwarded-For in each case.

  site A: no trusted_proxies configured   <- the shipped default
  site B: servers { trusted_proxies static 127.0.0.0/8 }

  $ curl -H "X-Forwarded-For: 9.9.9.9" http://127.0.0.1:9101/     # A
  remote_host=127.0.0.1 client_ip=127.0.0.1

  $ curl -H "X-Forwarded-For: 9.9.9.9" http://127.0.0.1:9102/     # B
  remote_host=127.0.0.1 client_ip=9.9.9.9

Reading:

  A - with no trusted proxy declared, {client_ip} IS the direct peer and the
      forged header is ignored. Identical to the previous {remote_host}
      behaviour, which is what makes the change safe to have made.

  B - once an upstream proxy is declared trusted, and only when the peer is
      in that range, {client_ip} resolves the real client out of the chain
      that proxy wrote.

Why it matters: without B, putting any reverse proxy in front of this stack
collapses every visitor into one per-IP rate-limit bucket and writes the
proxy's address into every audit row. Nothing fails visibly; the per-IP
limiting simply stops meaning anything. caddy/conf.d/README.md topology A
tells the operator to declare the proxy, and says why.

Reproduce: caddy/conf.d/README.md, topology A.
